# Свой тип встречи у гостя — одноразовый, только в брони

Status: accepted. Date: 2026-10-20.

## Context

Гостю нужно выбрать тип встречи из списка владельца или указать свой. Если создавать для этого обычный EventType, гость получит возможность менять список владельца, а брошенные попытки оставят «мусорные» типы. При этом владельцу всё равно нужно видеть, на какую встречу записались.

## Decision

Свой тип встречи передаётся в `BookingCreate` как `customEventType` (`title`, опциональный `description`) вместе с `owner_id`; `event_type_id` при этом не передаётся. Сервер сохраняет название и описание в самой Booking (`eventTypeTitle`, `eventTypeDescription`), но не создаёт EventType и не добавляет его в список владельца. Для существующего типа Booking хранит snapshot названия и ссылку `event_type_id`.

Слоты не зависят от типа встречи (уникальность — owner + slotStartAt), поэтому `GET /api/slots/` принимает `event_type_id` опционально: если он задан, проверяется принадлежность владельцу; если нет — слоты считаются для `owner_id`.

## Consequences

Плюс: гость может записаться на свою формулировку, список типов владельца не засоряется, владелец видит название встречи в брони. Минус: свой тип нельзя переиспользовать или отредактировать, а Booking получает snapshot-поля, которые нужно поддерживать при будущем изменении EventType.
